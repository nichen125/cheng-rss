# 澄（cheng）

自托管的**私人知识库**：订阅进来自动收集，AI 压一遍，剩下的留给你。
阅读体验对齐 Huntly，并在此之上提供自动化的分类分级、每日简报、跨篇聚合。
支持二进制 / 源码 / Docker 三种部署，一个数据目录即可备份迁移。

> 界面与视觉规格见 [docs/界面设计方案.md](docs/界面设计方案.md)；
> 静态草图与实现截图在 [docs/mockups/](docs/mockups/)，可以直接在浏览器里打开看。

> **当前状态：M0 / M1 / M2 / M3 / M4 完成**（骨架 + 三路部署 + 认证 + 队列 + 检索 + 阅读 +
> RSSHub + AI 分类分级与向量化 + 预算闸门 + 事件聚类与每日简报 + 简报页 + 划词高亮）。
> **v2.0 的四项也都已落地**：AI key 可在界面填写（2.6）、未分组源平铺侧栏（1.26）、
> 单篇总结 + 提示词可编辑（2.7）、资源与性能预算（0.10）。
> 53 个验收脚本全绿。
> 按 [PLAN.md](PLAN.md) 的分步计划推进，下一步是 M5（检索 + MCP 服务器）。
>
> **临时文件一律留在项目内**：验收与调试脚本写 `.tmp/`，不写系统临时目录。
> `verify-all` 收尾会自动清；手动清用 `node scripts/clean-tmp.mjs`（详见 PLAN §19.10c）。

**要跑 AI 分析，需要一个 OpenAI 兼容的 key**。两种给法任选其一：

```bash
# ① 环境变量（部署期注入，Docker / NAS 推荐）
AI_API_KEY=sk-xxx ./ai-rss serve --data ./data
# 换服务商就换地址与模型（设置页里也能改）
AI_API_KEY=sk-xxx AI_BASE_URL=https://api.deepseek.com/v1 ./ai-rss serve
```

```text
# ② 界面上填（单机日常用，推荐）
启动 → 右下角齿轮 → AI 分析 → 「API Key」卡 → 填 key → 保存 Key → 测试连接
```

界面填的 key 存在 `data/secrets.json`（权限 600），**不进 `app.db`、不进备份包、
不进导出**。两者同时存在时**文件优先** —— 它是用户显式填的那个。
存好之后不需要重启：分析队列下一轮就会自己用上它。

没有 key 时其余功能全部正常，只是不会产出摘要与分类。此时**不会逐篇刷日志**：
启动横幅写一次「未配置 API key，N 篇待分析」，设置页常驻显示状态与填写入口；
那批待分析条目也不会被标成 `failed` —— 它们只是排在队列里等 key。
（全局性失败按模板限速：同类日志每 60 秒最多 3 条，超出的折叠并计数。）

## 快速开始

### 方式 A：源码运行（开发推荐）

需要先有 Node 24。**所有依赖与工具链都装在项目目录内**，不污染系统。

```bash
git clone <repo> && cd ai-rss

# Linux / macOS
./scripts/bootstrap.sh      # 下载项目内 Node 24（约 34MB，只需一次）
./scripts/build.sh          # 构建前端 + 服务端
./.toolchain/node/bin/node --experimental-strip-types src/index.ts serve --data ./data

# Windows PowerShell
.\scripts\bootstrap.ps1
.\scripts\build.ps1
.\.toolchain\node\node.exe --experimental-strip-types src\index.ts serve --data .\data
```

打开 http://127.0.0.1:3000 ，首次访问会引导创建管理员账号。

### 方式 B：单文件二进制

```bash
./scripts/build.sh --sea               # 产出 dist/ai-rss-<platform>-<arch>[.exe]
./dist/ai-rss-linux-x64 serve --data ./data --port 3000
```

二进制内嵌了全部前端资源，**不需要旁边的 dist 目录**，复制单个文件即可运行。

### 方式 C：Docker

```bash
docker compose up -d
# 或
docker build -t ai-rss . && docker run -d -p 3000:3000 -v ./data:/app/data ai-rss
```

## 配置中心

订阅管理、分组、账户都收在一个弹窗里（左边选分类，右边改内容）。

**入口只有一个**：桌面是右下角的齿轮，手机是底部导航最后一格「配置」。
侧栏里没有单独的「订阅」按钮了 —— 它和齿轮打开的是同一个弹窗，留着等于
两个门；而手机上侧栏本来就隐藏，那一格是唯一的入口，所以保留位置但改名。

| 分类 | 现在能做什么 |
|---|---|
| 订阅 | 源列表、添加、编辑、批量管理、OPML 导入导出、全部刷新 |
| 分组 | 新建 / 重命名 / 删除，显示每组源数 |
| 账户 | 邮箱、显示名、角色、退出登录 |
| AI 分析 | 占位（M2）：模型 API、分类分级、重跑队列、提示词模板 |
| 每日简报 | 占位（M3）：生成时间与推送、聚合范围、跨源冲突、历史回看 |
| 备份与迁移 | 占位（M6）：备份保留份数、一键导出、恢复到干净实例、校验和 |

为什么是弹窗而不是加一栏：配置是低频动作，常驻一栏会永久吃掉 1/4 屏宽；
弹窗把主界面遮住，明确告诉你"现在在配置，不是在读"。

**切分类不会丢东西**：六个分类都挂着，只把非当前的藏起来。所以你在
「添加订阅」里填了一半地址、跑去「分组」看一眼再回来，输入还在。

**订阅页的分组筛选有两种形态**：分组 ≤ 2 个时是一排 chip（一次点击到
目标）；≥ 3 个时换成下拉栏 —— chip 行会随分组数换行，把源列表往下压，
而这一行的作用只是"选一个分组"。

## 收件箱阅读控制

列表标题行右侧有「全部 / 未读」和刷新按钮。

- **默认只看未读**。打开应用看到的就是没读过的，读过的要点「全部」才出来。
  这个默认值不记在本地：刷新页面回到未读，因为你点「全部」通常是"我现在
  想回看一条"，不是"以后都这样"。
- **全部 / 未读**：同一个列表的筛选，不是两个页面。点「未读」只留未读，
  点「全部」把已读的也放回来（已读的仍是灰的，一眼能区分）。它和侧栏的
  「未读」是同一份状态，点哪边另一边都会跟着变。
- **刷新**：重新拉当前视图，**保留**你现在的分组 / 源 / 搜索词。刷新时
  列表不会清空（不闪白），按钮转圈并禁用，防止连点。

为什么放标题行而不是单开一行：按 §15.2 的密度预算，一屏要看 8~10 条，
多一行控件就等于每屏少一条。

刷新和切视图的区别：切视图是**换条件**，刷新是**同一条件重新取数**。
所以读完一篇在别处被标成已读的文章，点一下刷新就能看到它的新状态。

## 三栏布局与密度

界面是三栏：**左＝范围**（收件箱/未读/收藏/历史 + 分组树）、**中＝列表**、
**右＝内容**。宽度是按"阅读优先"分配的：

| 断点 | 侧栏 | 列表 | 说明 |
|---|---|---|---|
| ≥ 1221px | 196px | 368px | 默认。1440 屏下正文区 876px，首屏 9 条 |
| ≤ 1220px | 184px | 344px | 先缩两栏，不让正文被挤窄 |
| ≤ 1024px | 184px | 320px | 平板，仍三栏 |
| ≤ 900px | — | 全宽 | 阅读区改成浮层，列表占满 |
| ≤ 640px | 0 | 100% | 单栏 + 底部导航 |

正文宽度默认 **80ch**（约 712px），可在阅读设置里改成 64 / 80 / 96。
超过 90ch 长行的回扫成本明显上升，所以不给更宽。

1440 屏下正文两侧各留 82px —— 这个数是量出来的：v1.13 时是 118px，
1920 屏下更是 358px，比列表栏（368px）还宽，等于把收窄两栏省下的宽度
又全丢回留白里。v1.14 放宽正文宽度后收到 82px，同时保留"呼吸区"
（完全贴边在宽屏上更累）。

两侧栏的尺寸是 v1.13 收窄过的（218/400 → 196/368）：改之前按"最坏情况"
定宽，实测平均标题只有 1.4 行、最长的分组名本来就走省略号，多出来的宽度
全被浪费。收窄后列表行内边距同步从 10/14 收到 9/12，
1440×960 下首屏从 8 条回到 9 条。

### 正文的"纸"与侧边目录

正文列不是直接铺在背景上，而是一张浮起来的**纸**：纯白底、16px 圆角、
一层很淡的阴影，而纸面之外的桌面是暗一阶的灰。这样宽屏上能一眼看出正文
在哪儿结束 —— 两侧那片留白才不像"没做完"。三个阅读主题（亮色 / 暗色 / 米色）
各有自己的纸色，切主题时边缘不会消失。

纸的宽度 = 正文宽度 + 内边距，所以你改阅读宽度（64/80/96）时纸跟着变，
不是写死的像素。手机上取消纸（铺满屏幕）—— 屏宽已经贴到内容，
圆角阴影只会白占 2px。

**侧边目录**在正文右侧的空白里，只列文章的小标题（h2/h3），点一下滚到那一段，
滚动时当前小节会高亮。两条规则：

- **只在放得下时出现**。判据是"扣掉正文后还剩多少宽"，不是视口断点 ——
  你把正文调到 96ch 之后纸变宽、空白变窄，写死的断点会失效并让目录压到
  正文上。实测 1440 屏（正文两侧各 53px）不显示，1600 屏起显示。
- **文章没有小标题就不显示**。实测 20 篇真实文章里只有长文（比如周刊）
  有 10 个左右小标题，短讯、日报、通稿一个是零个。1 个标题也不显示 ——
  单条目的目录没有导航价值。

**目录永不挤压正文**：它出现前后正文列宽完全一样，这是硬约束。
为此纸会向左偏约 100px（不是永远居中）—— 与其为了"绝对居中"把目录
推迟到 1750px 之后才出现，不如让纸偏一点换 1600px 就能用。

## 分组与编辑

几十个源之后，必须能归拢。分组是**一层扁平结构**（没有嵌套），理由是
一层就够用，而嵌套会让拖拽和删除的边界情况翻倍。

### 建分组

侧栏齿轮「配置」→「分组」→ 输入名字 →「新建」。重名会被拒绝
（大小写不敏感），避免「把这个源放进『科技』」变成有歧义的操作。

### 把订阅放进分组

两条路都行：

- **添加时直接选**：「+ 添加订阅」面板里有「分组」下拉，一次到位。
  默认跟随当前筛选 —— 你正看「科技IT」时加源，它就会落进「科技IT」。
- **事后改**：订阅行 → 铅笔图标 → 选分组 → 保存。同一个弹窗里还能改：

| 字段 | 说明 |
|---|---|
| 标题 | 留空则显示域名。RSS 自带的标题经常又长又带站点后缀，改短更好扫 |
| 分组 | 未分组 / 已有分组 |
| 抓取间隔 | 5 分钟 ~ 7 天。频繁更新用 30，周更博客用 1440 |

### 按分组看文章

侧栏「分组」下点组名 → 列表只显示该组的条目；同时这一组会在侧栏里
**就地展开**，把组内的订阅源逐个列在下面。标题旁有一个小小的 × 可以
退回全部。固定的「收件箱/未读/已收藏/历史」等价于"看全部"，点它们会
自动清掉分组筛选并收起分组树。

**分组不改变"读 / 全部"**：默认是只看未读，点进分组也还是只看未读 ——
切范围不该顺手把筛选也换掉。侧栏高亮此时给分组（一个位置只表达一件事），
"读 / 全部"的状态由列表头部的分段控件表达。

### 看分组里的某个订阅

展开的分组下面每个源占一行，行尾标着**该源的未读数**（0 也会显示 ——
"这个源没新内容"本身就是你想知道的信息）。

点一个源 → 列表只剩它的条目，标题变成「组名 · 源名」；再点同一个源
就回到整组。再点一次**组名**则收起这一组（组名同时负责"选范围"和
"展开/收起"，第二次点击的含义就是收起）。

同时只展开一组：侧栏高度有限，三组全开会把「收件箱」顶出视口。
换组时旧组自动收起。

> 这一块在 v1.13 之前是"列表头部一行横向滚动的 chip"。组里 11 个源时
> 那行吃掉 41px 高度，而且滚出去的那几个源等于看不见 —— 所以搬到了侧栏。
> 现在列表头部的高度与有没有选分组**完全相等**。

有两点在实现时特意处理过：

- **两个条件是真的叠加**。请求同时带 `folderId` 和 `feedId`，交集为空就
  返回 0 条，不会退化成"满足任一"。所以"组A + 组C的源"是空列表而不是错乱。
- **筛选态会自愈**。你正筛着某个源，然后去配置里把它移出组 —— 回来时
  会自动退回"整组"，**但分组保留**。不自愈的话侧栏里那个源还高亮着，
  列表永远是空的；自愈时顺手把分组也清掉，你会以为自己被弹出了分组。

### 删分组

在配置 →「分组」里删。组里的订阅**不会**被删，会退回「未分组」。
这是刻意的：删分组是最容易误触的操作，让它连带删掉 20 个订阅是灾难。

### OPML 带上分组

导出时会保留分组层级（分组是一个包住订阅的 outline），换到别的阅读器
后分组还在。导入同理——按名字复用已有分组，重名不报错。

## 一键批量管理

导入 OPML 之后第一件事不是读文章，而是把 20~30 个源收拾一遍。逐行点
五下 ×30 行没人做得完，所以有批量模式。

配置 →「订阅」→「管理」→ 每行左侧出勾选框，顶部出批量栏：

| 操作 | 说明 |
|---|---|
| 全选 / 清空 | 作用于**当前筛选后**的源。先点「科技IT」再全选，只选这 3 个 |
| 组头勾选框 | 只选这一个分组，不动其它组 |
| 移到分组… | 下拉里选目标组；选「未分组」即移出 |
| 恢复 / 暂停 | 恢复 `broken` 的源会同时清零错误计数并让下次抓取立刻到期 |
| 刷新 | 入抓取队列；暂停的源自动跳过（刷新它们等于假装刷了） |
| 删除 | 唯一需要确认的操作，确认框会写明"未读 N 条会一起删" |

**为什么是四个批量接口而不是前端循环**：32 个源移进分组时前端循环调用，
第 17 个失败（并发写锁）就变成"一半在组里"——用户还得手动找出来哪个没进去。
批量接口在一个事务里做完，要么全成要么全不成，而且只走一个往返。

混入已删除的 id 不会整体失败（另一个标签页刚删掉一个源不该阻断这次操作），
但会在结果里报 `missing`，不会静默吞掉。

## 阅读页

### 两个出口：原文 与 源站

读完一篇后想继续看的地方有两种，对应两个不同的入口：

| 入口 | 去哪 | 在哪 |
|---|---|---|
| 打开原文 | 这篇文章本身 | 阅读栏 `↗` / 标题 / 文末按钮 / 快捷键 `v` |
| 去源站 | 这个订阅的站点首页 | 阅读栏 `<RSS 图标>` / 站点名 / 文末「访问源站」 |

两者都是新标签打开，不离开阅读器。网页捕获的条目（没有源）不渲染源站入口，
不是渲染一个死链。

### 正文里的链接不再把阅读器跳走

改之前实测：正文 3176 个链接里有 2196 个（69%）**没有 `target`**，点一下就在
主框架里导航走了 —— 当前筛选、已加载的列表、滚动位置全部丢失，得按浏览器
后退才回得来。点一次就丢上下文，体感等同于"链接不能点"。

现在在清洗层统一加 `target="_blank"`，两类例外：

- **页内锚点**（`#xxx`）：同一文档内定位，新开标签等于把用户丢进一个只有片段
  的新页。清洗是幂等的（详情接口每次请求都会重洗一遍），所以第二次看到它
  already 是绝对 URL 时也要能认出来 —— 这是实现里最容易翻车的一处。
- **`mailto:` / `tel:`**：交给系统处理，浏览器本来就不导航。

### 列表行可以用中键打开

行元素是 `div[role=button]`（不是 `<button>`），标题是真 `<a href>`：

- 左键点行任意处 → 在右侧阅读区打开（原行为不变）
- **中键 / Ctrl+点击标题 → 在新标签打开原文**（浏览器原生行为）
- `Tab` 能聚焦到行，`Enter` 打开

为什么不能直接往 `<button>` 里塞一个 `<a>`：HTML 内容模型禁止交互元素嵌套。
所以这不是"加个链接"，是必须换行元素，再把按钮语义（`role` + `tabindex` +
Enter/Space）手工补回来。

### 已读可回退

阅读栏有「标为未读」按钮，快捷键 `m`。误点开一篇之后不用再去改数据库。

**阅读历史不清零**：`first_read_at` / `last_read_at` / `read_count` 保持原样。
"读过了"是事实，"不想让它算未读"是视图层的意图，两者不能互相污染 ——
否则 unread 一次就把「历史」页里的记录抹了。

## 正文提取

很多源的 feed 只给一段导语，点开阅读区只有两行字 —— 用户会以为这个源质量差，
实际是我们没去抓原文。抓与不抓的规则只有一条：

```
feed 正文（去标签后的字数） < 500  →  抓原文跑 Readability
否则                              →  直接用 feed 正文
```

不无条件抓的理由是算术：50 个源 × 每天 500 条 = 每天 500 次额外请求，而其中
大多数 feed 本来就带全文。抓了只是把网页原样抄一遍，还多一份对方站点的日志。

| 情况 | 结果 |
|---|---|
| feed 正文够长 | `extracted_by=feed`，一次网络请求都不发 |
| 只有摘要 + 原文可抓 | 抓原文 → Readability → 清洗 → `extracted_by=readability` |
| 原文 404 / 超时 / 是 PDF | 保留 feed 正文，原因写进 `stage_error`，约概不重试 |
| 提出了但内容不比 feed 多 | 保留 feed 正文（`no-improvement`），不塞一段错内容 |

**失败不重试**是刻意的：`extract` 只有 4 个并发槽位，为一个 404 重试 3 次就是
3 次白占槽位，而用户已经有可读的 feed 正文。条目的 `stage` 照常推进到
`extracted`，不会卡在 `pending`。

"提出了但不够多"的门槛是 `max(500, feed 字数 × 1.2)`。1.2 倍余量是因为
Readability 会剥掉导航、作者栏、相关阅读，字符数略少于页面是正常的；但若比
feed 正文还短，说明它抓错了节点（页面里有多个 `<article>` 时很常见）。

实测（真实页面，Node 24.13 / Windows x64）：

| 站点 | 页面体积 | 耗时 | 提取字数 / 语义容器字数 |
|---|---|---|---|
| jvns.ca | 31 KB | 50 ms | 0.93 |
| simonwillison.net | 77 KB | 128 ms | 1.00 |
| tonsky.me | 37 KB | 46 ms | 0.99 |
| martinfowler.com | 26 KB | 34 ms | 0.92 |
| blog.nelhage.com | 22 KB | 30 ms | 0.94 |

这五个页面已落成离线夹具（`tests/fixtures/extract/`，共 252 KB），验收脚本不打外网。

## 去重

同一篇文章常被几个源同时推到，直接入库就是时间线里出现两遍。判重分三层，代价从低到高，命中即停：

| 层 | 判据 | 吃掉什么 |
|---|---|---|
| 1. URL 规范化 | 去掉 `utm_*`/`fbclid`/`gclid`/`spm`/`ref`/`share_*`、fragment、末尾斜杠、host 大小写 | 同一地址被转发到不同渠道 |
| 2. 内容指纹 | 标题 + 正文前 2KB 的 sha1 相同 | 逐字转载 |
| 3. 向量余弦 | 256 维本地指纹向量，余弦 > 0.95 | 改了标题 / 加了导语 / 挂了版权声明的转载 |

第 3 层不能省：真实转载几乎总会改一两个字或加一段导语，那点改动足以把 sha1 完全打散 —— 实测四种转载变体（标题加站名、加版权声明、加导语、改开头一句）的余弦都在 0.99 以上，而 sha1 全不同。

**保留而不是丢弃**：判重命中的条目照样入库，只是把 `duplicate_of` 指向原件。时间线里不显示（那是去重的目的），但"这篇文章被几个源报道"可查 —— M3 的热度排序要用。排查"为什么某条没显示"时可以加 `?includeDuplicates=1`。

**阈值与代价**：
- `> 0.95` 判重复，`0.88~0.95` 判「同事件不同报道」（不合并，M3 聚类用）。异文实测最大余弦 0.17，区分力足够。
- 向量只对**近 14 天**的候选做比较（一次 400 条上限），更早的向量由每日维护任务清掉 —— 否则 10 万条 × 1 KB = 100 MB 白占 NAS 空间。
- 正文不足 40 字的不写向量：特征太少时余弦会虚高，写了只会制造误判。

> 已知限制：14 天前发布、今天才被转载的文章，第 3 层看不到它（URL 与指纹两层仍兜底）。这个窗口是"资源占用 vs 漏判"的取舍，不是实现缺陷。

## 阅读历史

侧栏「历史」按**你读的时间**倒序排列，分四组：**今天 / 昨天 / 本周 / 更早**。

几个容易踩的细节，都是按实际观感定下来的：

| 细节 | 为什么这么做 |
|---|---|
| 分组用**本地日历日** | 用毫秒差算会把"凌晨 1 点读的"和"23 小时前读的"算成同一天；用 UTC 算，东八区凌晨读的东西会跑到「昨天」 |
| 「本周」是**最近 7 天**，不是自然周 | 周一时按自然周算，周日读的会掉进「更早」，而它才过了一天 |
| 空分组不渲染 | 4 个空标题会让人以为加载失败 |
| 行内时间显示**读的时间**，发布日期进 `title` 提示 | 历史页的坐标是"我什么时候读的"；两者混成一个字段就分不清"这篇很旧但我刚读"和"刚发布我就读了" |
| `read_count > 1` 才出现 **×N** 角标 | 回看过的文章值得一个信号，它是收藏之外的另一个维度 |
| 分组标题**粘性定位** | 滚到第 40 条时，用户必须知道自己在哪个时间段里 |

**标记未读不会清空阅读历史** —— 「读过了」是事实，「不想让它算未读」是视图层的意图。两者混在一起的话，误点一次「未读」就把历史抹了。

## 添加订阅

启动后打开 UI → 侧栏齿轮「配置」→ 左侧「订阅」→「+ 添加订阅」，贴任何地址都行：

（这一步打开的是配置弹窗，停在「订阅」分类。面板里的「分组」下拉可以直接把新源放进某个组。）

| 你贴的 | 会发生什么 |
|---|---|
| 完整 feed URL（`https://x.com/feed.xml`） | 直接订阅 |
| 网站首页（`https://sspai.com`） | 从页面 `<link rel="alternate">` 找订阅地址 |
| 裸域名（`sspai.com`） | 补 `https://` 再按首页处理 |
| 一段带 URL 的文字 | 抠出第一个 URL |
| 找不到 `<link>` 的站点 | 探测 `/feed` `/rss` `/atom.xml` 等 14 个常见路径 |

发现到**多个** feed 时会让用户选，不替他挑。订阅前会先真抓一次 ——
拉不到内容的源不会进列表，所以"订阅成功但空的"不会发生。

也可以导入别的阅读器导出的 OPML（文件夹层级会保留），或导出自己的订阅。

### 没有原生 RSS 的站点：RSSHub 搜索

很多站点（B 站、知乎、YouTube 频道）不提供 RSS。同一个「添加订阅」面板里点
**「用 RSSHub 搜」**，输关键词或直接贴网址，就能拿到可订阅的地址：

| 你输入 | 走哪条路 |
|---|---|
| `哔哩哔哩` / `bilibili` | 在本地路由库里按命名空间、路由名、说明、分类、路径匹配 |
| `https://www.bilibili.com/video/BV1xx` | Radar 按域名反查出该站的路由 |
| `hotlist` | 按路径片段匹配 |

搜到候选后**选中一条**，路径里的 `:uid` 这类占位符会变成输入框（示例值已预填），
点「预览最近几条」真的抓一次 —— **看到条目之后**才出现「订阅这个地址」。

必须先预览的原因：不预览就订阅，等于把一个可能是死链的地址存进库里，
之后它在订阅列表里永远标「失效」，而用户完全不知道为什么会这样。

**实例与缓存**：

- 默认用公共实例 `https://rsshub.app`。公共实例有速率限制，建议在配置里填自建实例地址（支持 `accessKey`）。
- 路由库（几百 KB）缓存 **7 天**，搜索全本地、不打上游。过期后仍可用，只会提示一句「去刷新一下」—— 上游挂掉时还能搜到东西，比空白页有用。
- 首次启动且断网时用 5 条内置路由兜底（B 站 / 知乎 / 少数派 / GitHub / YouTube），不至于一打开就是空白。

### 抓取行为

| 行为 | 值 | 说明 |
|---|---|---|
| 默认间隔 | 30 分钟 | 添加后可改，最小 5 分钟 |
| 条件请求 | ETag / Last-Modified | 304 时不重复入库，也不消耗解析 |
| 失败退避 | 间隔 × (1 + 失败数×2)，最多 7 倍 | 成功一次即复位 |
| 置 `broken` | 连续 3 次失败，或 404/410 | 不再自动重试，UI 标「失效」 |
| 取消订阅 | 未读条目删除；**已读/已收藏保留** | 历史记录不该因为退订而消失 |

正文在入库前过白名单清洗（`feeds/sanitize.ts`），读出来时再洗一次 ——
feed 是外部输入，`<script>`、`onerror`、`javascript:` 都必须拦掉。

#### 关于 `m0-09-ui` 的浏览器依赖

它用本机 Edge/Chrome 的**无头模式 + 裸 CDP** 验布局，不下载 playwright。
找不到 Chromium 系浏览器时整节 SKIP（退出 0）并打印说明 —— 环境缺失不算失败，
但 SKIP 会在汇总里看得见，不会静默通过。

为什么需要它：其余脚本全是行为断言（状态码、字节数、耗时），一个布局错乱、
正文只有 66 字符宽、或者点开条目就跳页的界面能让 9/9 全绿。

#### 关于 `docker-path` 的产物验证

它需要一份 **linux 版 node** 作为 SEA 的注入底本（约 25MB），用来验证
Dockerfile 里 `build-sea` 那一步真能产出能跑的 ELF。首次运行：

```bash
node scripts/fetch-linux-node.mjs      # 一次，之后走 .tmp/linuxnode 缓存
node scripts/verify-all.mjs            # 这时 docker-path 是 12/12
```

**没有这份 node 时，`docker-path` 会报 FAIL 而不是假装通过** ——
"没验证"和"验证通过"是两件事。离线环境可显式接受跳过：

```bash
node scripts/verify-all.mjs --allow-skip-docker-artifact
```

此时会明确提示"这不等于构建路径已验证"。

### 跨平台构建

SEA 的注入底本必须是目标平台的 node 可执行体。所以：

```bash
# 在 Windows 上造 Windows 产物（默认）
node scripts/build-sea.mjs

# 在 Windows 上造 Linux 产物：需要一份 linux 的 node
AI_RSS_SEA_BASE=./vendor/node-linux-x64 \
  node scripts/build-sea.mjs --target linux-x64

# 不提供底本时会明确拒绝，而不是产出一个跑不起来的文件
node scripts/build-sea.mjs --target linux-x64
# ✗ 不能从 win32-x64 造 linux-x64 的二进制。
```

Docker 构建天然满足这一点（容器里跑的就是 linux node），所以 `Dockerfile` 里
直接写 `--target linux-x64`。

## 已知限制

- **SEA 不支持 Alpine（musl）**：Docker 用 `debian:bookworm-slim`
- **不发布 macOS 二进制**：SEA 官方只测 arm64
- **Docker 镜像未在真机上构建过**：开发机没装 docker。Dockerfile 的每条指令已
  本地逐条验证（`scripts/verify/docker-path.mjs`），并且**真的产出了能内嵌资源的
  linux-x64 ELF**，但 `docker build` 本身没跑过。首次在有 docker 的机器上构建时
  请留意：若失败，最可能的原因是 `package-lock.json` 与容器内 npm 版本差异。
- **订阅已可用**：RSS 2.0 / Atom / RDF、OPML 导入导出、自动发现地址、定时抓取、条件请求
- **AI 分析已可用（M2）**：条目入库后自动排队做摘要 / 要点 / 分类 / 分级 / 向量化。
  没有 key 时不产卡片，也不影响阅读；有 key 但预算超了会在设置页显示原因是哪一档。
  **未做的一件人工事**：PLAN §19.4 的黄金测试集（20~30 篇人工标注、算摘要准确率与分类
  混淆矩阵）需要真实模型跑一次作为回归基线，尚未做 —— 其余判据都已自动验证
- **AI 的成本是"记调用不记条目"**：一次因格式不合规重试的分析记两条 `ai_usage`。
  看「今日调用 N 次」时要知道它数的是请求次数
- **每日简报已可用（M3）**：每天 08:00（可改）把最近 24 小时聚成事件、跨源归纳，出一份
  带脚注引用的简报。**没有内容时不出**，并在设置页写明原因（"最近 24 小时没有新条目"）。
  两个已知取舍：
  · **引用是脚注号而不是内联链接** —— 模型只能写 `{{cite:簇id}}`，由程序替换。它写的
    裸 URL 一律被抹成「链接已移除」，因为校验 URL 合法性挡不住"链接是真的但指向的不是
    这件事"，而伪造链接的失败模式是"有链接但错"，用户点了才知道
  · **hash 向量聚类的召回有上限** —— 没配 embedding 时用本地字符 n-gram 指纹，同一件
    事的两篇如果连实体名和数字都换了就聚不起来（余弦 0.25~0.35，低于阈值 0.35）。
    这是能力边界不是 bug；配了 embedding 后走语义向量（阈值 0.80）。m3-01 有两条
    断言把这个边界固定住，防止有人为了让"同事件都能聚"而调低阈值 —— 那样无关事件
    会立刻误聚
- **简报的误聚率需要真人验**：PLAN §19.5 的门禁是"连跑 3 天、人工评估误聚 < 10%"，
  自动部分只能验结构正确性（能聚、不误聚、引用不伪造、重跑不重复）
- **划词高亮已可用（M4）**：选中正文任意一段即可标黄/绿/蓝、加批注、让 AI 解释这段。
  高亮按**整篇纯文本的字符偏移**存储，正文被重新提取后按 position → quote+上下文 →
  quote 唯一 三级降级重新定位；三级都失败时标 `is_orphaned`，在阅读页单独列一段
  「原文已变化，无法定位」——**保留而不是删除**，删掉用户就再也找不回来了。四个取舍：
  · **`range`（XPath）降级没在服务端做** —— XPath 是浏览器侧表示，服务端既无法验证
    也无法在正文重提后重算，回写结果在下一次正文变更时立刻失效。所以服务端判不了就
    不假装判，两级失配即 orphaned。这比 PLAN 原表少一级（§11.1b 记了收窄理由）
  · **高亮按纯文本定位，不按 HTML** —— 按 HTML 的话一次清洗规则调整（`<br>` → `<p>`）
    就会让全文偏移全变；按纯文本则不受标签变化影响。代价是跨段选区被压成一行
  · **客户端要复刻一份 HTML→纯文本映射**，规则必须与服务端 `htmlToText` 逐条等价
    （块级元素补一个空格、连续空白折叠、首尾 trim）。不等价的表现是**高亮画在别的
    字上而画面完全正常**，所以 `m4-03` 专门有一条"刷新后只靠服务端 pos 重画"的断言
  · **AI 联动只做了三项**（解读 / few-shot 校准 importance / 简报小节），
    高亮向量聚类与 RAG 提权要等 M5 的向量层与检索层，现在做等于返工
- **高亮 few-shot 对冷启动无效**：不足 3 条近期高亮时**不注入**（1~2 条说明不了兴趣，
  只会把文章往"用户关心"硬掰）。所以最初几十篇分析的 importance 完全是模型原判
- **正文提取按需触发**：feed 自带全文（≥500 字）就直接清洗入库、**不抓原网页**；
  只有摘要的条目才抓原文跑 Readability。失败（404 / 非 HTML / 提出内容不够多）时
  回退 feed 正文并在 `stage_error` 记录原因，条目不会丢也不会卡在 pending
- **去重三层已全开**（URL 规范化 / 内容指纹 / 256 维向量余弦）：重复条目不进时间线但保留
  入库（`duplicate_of` 指回原件）。向量只覆盖近 14 天候选，更早的由每日维护任务清理；
  这条取舍的边界见上文「去重」一节
- **RSSHub 搜索可用，但依赖上游**：路由库来自 RSSHub 的 `/api/namespace` 与
  `/api/radar/rules`，公共实例有速率限制且路由不保证全（自建实例可填地址与
  `accessKey`）。预览走的是拼出来的地址，若那条路由在上游已失效，会直接报
  「没有解析出任何条目」而不是静默订阅死源
- **简报页已可用（3.5）**：侧栏「简报」是一等入口（桌面侧栏 + 移动端底部 tab 第 5 格）。
  左栏日期列表、右栏正文；今日要点三条、事件分组（一致/分歧）、值得一读、脚注可点。
  三个取舍：
  · **引用表是落库快照**（`digests.cites`），不是从正文反查 —— 3.3 的 `renderCitations`
    在落库前就把 `{{cite:cl_x}}` 换成了 `[1]`，反查永匹配不到。标题一并存下，簇被
    整窗重算清掉后脚注仍是文字而不是 `[1]` 空号
  · **Markdown 自己解析成 React 节点**，不用 `dangerouslySetInnerHTML` —— 模型输出
    不经 HTML 解析就没有注入面。代价是只支持 6 种语法（标题/段落/粗体/列表/分隔线/脚注），
    表格与嵌套引用不渲染
  · **脚注点开是浮层卡片不跳页** —— 读正文到一半点 `[2]` 要知道"第 2 条是哪件事"，
    跳走会丢失阅读位置。代价是长正文里卡片 sticky 在底部，可能与正在读的段落错开
- **侧边目录只在宽屏出现**：正文 80ch（712px）+ 目录 190px 要 986px，加上外层留白
  要 1034px 面板宽，即视口 ≥1600px。1440 笔记本上不显示是**故意的** —— 与其为了
  显示目录把正文压窄（等于把 v1.14 刚放宽的宽度收回去），不如不显示
- **纸会向左偏约 100px**：为了让目录在 1600px 就能出现，显示目录时纸与目录作为一个
  整体居中。代价是正文不再绝对居中，但这个偏移只在有目录时发生，且正文宽度不变
