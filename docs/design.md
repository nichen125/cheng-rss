# 设计

本文记录**界面规格与几个非显然的算法决定**。每条都写清了"为什么不那样做"，
因为这些东西三个月后最容易被人"顺手改掉"，而改掉的理由往往看起来更合理。

界面视觉规格的完整版与静态草图见：
- [界面设计方案.md](界面设计方案.md) —— 配色、密度、控件尺度
- [mockups/](mockups/) —— 可直接在浏览器打开的 HTML 草图与截图

## 界面结构

三栏，左侧可收：

```
┌────────┬──────────────────┬─────────────────────┐
│ 订阅源  │   条目列表         │   正文              │
│ 分组    │   (按重要度排)     │   + AI 摘要/要点    │
│ 简报    │                  │   + 右侧目录         │
│ 设置    │                  │   + 高亮            │
└────────┴──────────────────┴─────────────────────┘
```

**左侧栏不是导航，是数据。** 它的每一项（收件箱、分组、单源）都是一个筛选条件，
带未读计数。这个设计来自 Huntly：它比"点进一个页面再筛"少一次跳转。

### 三栏密度的取舍

断点是四档，第一档先缩栏宽再缩正文 —— 正文宽度是阅读体验的硬指标，
侧栏宽度只是导航舒适度：

| 宽度 | 布局 | 侧栏 / 列表宽 |
|---|---|---|
| ≥1220px | 三栏，舒适 | 默认 |
| ≤1220px | 三栏，栏宽收窄 | 184 / 344 |
| ≤1024px | 三栏，列表再窄 | 184 / 320 |
| ≤900px | **两栏**（侧栏 + 列表），正文覆盖 | 读数 |
| ≤640px | 单栏 + 底部 tab | — |

**为什么不做 4 栏或可拖拽宽度**：拖拽宽度的实现成本低，但它让"布局"变成一个
用户需要维护的状态（拖坏了怎么恢复？）。固定的三档断点更好。

## 正文提取

用 Mozilla Readability + linkedom（纯 JS DOM，无原生依赖）。

### 为什么不用 `@mozilla/readability` 的默认清洗

Readability 保留 `<figure>`、`<img>`、部分 `<div class="ad">`。对"存档"来说这是对的，
对"喂给模型"来说导航残渣会浪费 token 并干扰判断。所以在 Readability 之后
还有一层**确定性清洗**（不是模型清洗）：

| 步骤 | 做法 |
|---|---|
| 去导航残渣 | 匹配"上一篇 / 下一篇 / 相关阅读 / 首页 >"等模式，只删段尾 |
| 去版权声明 | "转载请注明 / 本文来自 / 责任编辑 / 版权归"，只删最后 300 字内 |
| 图片 alt 处理 | `htmlToText` **不**拼 alt（图注常是"图片描述：xxx"，对模型是噪声） |
| 空白归一 | 连续空白折叠、中文标点统一 |

> 清洗规则是**确定性**的，因为它要可预测。用模型清洗会用一次调用换一点 token，
> 净成本更高，且不可复现。

### 存什么

正文存两份：
1. `entry_contents.html` —— gzip BLOB，原始 HTML 清洗后的结果（阅读页用）
2. 运行时 `htmlToText()` —— 纯文本（喂模型用）

**不存纯文本的第二份**：它可以从 HTML 无损重算，存两份会产生"哪个是最新"的问题。

## 去重

两层，先便宜后贵：

| 层 | 方法 | 何时用 |
|---|---|---|
| URL 级 | 规范化后比 `url_norm` | 永远先跑 |
| 内容级 | SimHash 近似（汉明距离 ≤ 3） | URL 不同时 |

**为什么不用精确内容哈希**：同一篇文章被不同源转载时，正文几乎总有细微差异
（广告位、编辑改标点、来源标注）。精确哈希一条都判不出来。

**为什么 SimHash 而不是 MinHash**：SimHash 的实现是"分词 → 加权 → 64 位指纹"，
一个函数就能写完，且在"近似重复"这个场景足够准。MinHash 需要多个哈希函数与
更长的签名。

## 聚类

同一件事的多篇报道聚成"事件"。

### 两种向量，一条阈值链

| 模式 | 向量来源 | 阈值 | 召回 | 成本 |
|---|---|---|---|---|
| 语义 | embedding 模型（如 `text-embedding-3-small`，1536 维） | **0.80** | 高 | 每次分析一次调用 |
| 兜底 | 本地字符 n-gram 指纹（维度较低） | **0.35** | 低 | 免费 |

阈值差这么多的原因：两种向量的**余弦分布完全不同**。语义向量的"不相关"也在
0.3 左右，所以 0.80 才叫"很像"；字符指纹的"不相关"接近 0.05，0.35 已经很接近了。
把两者统一成一个阈值是错的。

**兜底模式的能力边界**：同一件事如果连实体名和数字都换了，就聚不起来。
这是**能力边界而不是 bug**，验收脚本 `m3-01` 里有两条断言专门把这个边界固定住，
防止有人为了让"同事件都能聚"而调低阈值 —— 那样无关事件会立刻误聚。

### 为什么不做"全局聚类"

聚类窗口是**最近 24 小时**，不是全库。全库聚类有两个问题：
- 成本随库增长（每次简报要算 N² 相似度）
- 昨天的简报表今天会被改写，而它是已经推送出去的东西

## 引用与防伪造

简报正文由模型写，但**它不能写链接**，只能写 `{{cite:cl_x}}`（簇 id）：

```
模型输出：  两家公司同日宣布量产{{cite:cl_1}}，但位密度的说法不一致{{cite:cl_2}}。
渲染之后：  两家公司同日宣布量产[1]，但位密度的说法不一致[2]。
              └─ 点击 [1] 打开浮层，显示 cl_1 是哪几篇报道
```

`cl_1` → 哪几篇文章的对应关系存在 `digests.cites`（JSON 快照），
**不是**从渲染后的正文里反查 —— 反查不可能，因为 `{{cite:}}` 在落库前已经被
换成 `[1]` 了。

### 为什么裸 URL 一律抹除

模型有时会自己写 `https://...`。这个链接可能是真的，但它**指向的不一定是这件事**：

- 模型把"某公司的官网"当成"这条新闻的原文"
- 模型把相似事件的旧新闻链接安到新事件上

校验 URL 是否合法挡不住这个 —— 因为它确实是合法 URL。所以策略是：
**只允许引用我们自己的簇 id，裸 URL 一律替换成「链接已移除」**。
失败模式是"没有链接"而不是"链接是错的"。

无效的簇 id（模型编的 `cl_99`）渲染成 `[?]`，并在返回值里计入 `invalidCites`。

## 划词高亮

选中正文任意一段即可标色、加批注、让 AI 解释。

### 三选择器降级（关键设计）

高亮的位置用**整篇纯文本的字符偏移**存储。但正文可能被重新提取（源站改版、
Readability 升级），偏移就失效了。所以定位是三级降级：

```
① position（字符偏移）      —— 最快，正文没变时准确
    ↓ 失败
② quote + 上下文            —— 在窗口内搜这段文字，取最接近原偏移的那个
    ↓ 失败
③ quote 唯一                —— 全篇搜这段文字，只有一个匹配才用
    ↓ 失败
   标 is_orphaned，在阅读页单列一段「原文已变化，无法定位」
```

**三级都失败时保留而不是删除**：删掉用户就再也找不回来了。留着的成本是一行数据，
删掉的成本是用户的一次劳动。

### 为什么 `range`（XPath）降级不在服务端做

XPath 是浏览器侧的表示，服务端既无法验证也无法重算它。所以 `range` 只作为
前端的提示存在，不作为服务端的定位依据。

## 顺序与排序

分组与源都可以调顺序（长按拖动或配置页的 ↑↓ 箭头）。

### 两个入口的原因

手机上侧栏是 `display: none`（换成底部 tab），长按拖动**摸不到**。
所以配置页必须另有一路常显的 ↑↓ 箭头。

### 每次落位即提交

拖动结束立刻 `PATCH`，不做"先改本地再统一保存"。原因：
- 拖到一半刷新页面，本地状态就丢了
- 用户不知道"改了但没保存"

代价是拖 10 次发 10 个请求。可以接受 —— 排序是低频操作。

### 长按判定的坑

长按拖动与浏览器的原生行为冲突：

| 行为 | 不加处理时 |
|---|---|
| 手机长按 | 弹出系统菜单（复制/搜索） |
| 手势滚动 | 页面跟着滚，拖动变不了位 |
| 触摸滑动 | `touchstart` 后浏览器抢走手势 |

解法是 `touch-action: pan-y`（允许纵向滚动，禁止横向与长按手势）+ 500ms 定时 +
8px 位移阈值（超过阈值判为滚动，取消长按）。`user-select: none` 只挂在侧栏，
**不能提到 `body` 或 `.settings-card`** —— 否则阅读页与配置页都选不了字，
而画面完全正常，看不出问题。

## 每日简报的三种否决

不是每天都有简报。三条否决路径各有独立的持久痕迹：

| 否决 | 条件 | 记录在哪 |
|---|---|---|
| 没到时间 / 今天已生成 | `digestDue` 判定 | 不记录（正常状态） |
| 没内容 | 24h 内无条目 | `digest_skips` |
| 簇不够 | 少于 2 个事件 | `digest_skips` |
| 生成失败 | 模型返回不合规 | `digest_attempts`（`ok=0`） |

**为什么要分开记**：这三种的处置完全不同。没内容是正常的（用户知道今天没新闻）；
生成失败要退避重试。混在一起的话，"今天为什么没简报"这个问题在日志里答不出来。

### `day_key` 是独立的一列

`period_start` 与"哪一天"是**两件事**：
- `period_start`：这份简报覆盖的时间窗起点
- `day_key`：这份简报属于哪一天（本地日 00:00）

分不开的后果：用户把生成时间从 08:00 改到 09:00，`period_start` 变了，
唯一索引就认为这是新的一份，于是同一天出现两份简报。

> 这一列在 v2.2 之前**从没被写入过**（INSERT 的列清单漏了它），导致唯一索引
> 从未生效、调度器每分钟重跑一次完整流程。细节见 [PLAN.md §9.6](../PLAN.md)。

## 移动端

- 断点：640px 以下单栏 + 底部 tab（6 个）
- 正文 tab 与列表 tab 是**互斥的整屏**，不是可滑动的面板 —— 滑动面板会和
  横向滚动、划词选择冲突
- 所有可点目标的最小尺寸 **44×44px**（触摸红线）。配置页的折叠头、
  列表行、侧栏项都按这条量

## 视觉克制

有意**没有**做的事：

| 没做 | 原因 |
|---|---|
| 冲突用红色 alert | 简报里的"分歧"是信息不是错误。红色会让人以为出了问题 |
| 骨架屏 | 列表从缓存渲染，通常 <100ms。骨架屏反而闪一下 |
| 动画过渡 | 除了长按拖动的悬浮反馈，其余不加。阅读场景要静 |
| 深色模式切换按钮 | 跟随系统。手动切换会让"明明设置了深色为什么还是浅色"变成常见问题 |
